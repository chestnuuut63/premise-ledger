# 使用实例：一位烘焙店主与 agent 的一次真实合作

> 这份文档回答一个问题：**用户和 agent 聊天的时候，premise-ledger 到底在哪一刻被叫起来，叫起来之后改变了什么。**
>
> 文中所有输出都是 `python demo_scenario/run_scenario.py` 的真实结果，可逐行复现。

---

## 一、为什么需要它：一句话

**用户不是在问一道题，是在和 agent 一起改一份测算。** 改的过程中，前提会被更正、补充、否掉；而结论还挂在旧前提上。

单轮问答看不出问题——每一轮 agent 都答对了。问题出在**第 9 轮还在用第 2 轮的数**，而这件事没有任何一步会报错。

所以这个 skill 的位置很明确：**它不是替 agent 算，是替 agent 记账。**

---

## 二、场景设定

| | |
|---|---|
| **用户** | 一位烘焙店主，想在小区门口开第二家店，判断多久能回本 |
| **任务** | 9 轮对话，从口述数据到准备把结论发给合伙人 |
| **为什么需要账本** | 用户中途更正了租金（8 万 → 9.5 万），前面已经算过 6 条结论；没有账本，没人知道哪几条该重算 |
| **用户不懂代码** | 全程只说人话，不接触任何命令。所有 `ledger` 调用都是 agent 在后台做的 |

---

## 三、三个接入点：它什么时候被叫起来

这不是"每句话都记账"——那会烦死人。只有三个时刻强制：

| 接入点 | 触发条件 | 账本做什么 |
|---|---|---|
| **① 结论要对外** | 用户说"发给合伙人""写进材料" | 门禁检查：上游前提是否都已核实。未核实 → `exit 1`，不许交付 |
| **② 用户改口径** | "其实是 9.5 万""那个数作废" | 撤回旧前提，返回**恰好哪几条结论作废、哪几条不受影响** |
| **③ 用户追问来源** | "这个 -5 万怎么算出来的" | 返回结论卡片：依赖哪几条前提，其中哪几条还没核实 |

其余时候它静默记着，不打断对话。

---

## 四、9 轮实录（节选真实输出）

### 第 1 轮 · 开工

> 👤 我想在小区门口再开一家烘焙店，你帮我算算多久能回本？

> 🤖 可以。但先说清楚：下面所有数字都要能追溯到来源，中途你改了哪个，我会告诉你哪些结论跟着作废。

```
$ ledger new --task 社区烘焙店二店回本测算
← 账本已建立（空）
```

**这一轮没有任何计算。** skill 做的第一件事是把"这次对话要留痕"这件事说清楚——用户从第一句就知道，改口是有代价的、也是被允许的。

---

### 第 2–3 轮 · 登记前提，并区分"你说的"和"我猜的"

> 👤 租金一个月 8 万，客单价大概 26 块，装修加设备 60 万，店里 4 个人、一个人 7000。毛利大概 62%。

```
← A1  月租金 8 万元            [unverified, conf=0.5, src=user]
← A2  客单价 26 元             [unverified, conf=0.5, src=user]
← A3  装修与设备一次性投入 60 万元  [unverified, conf=0.5, src=user]
← A4  人工 4 人，人均月薪 7000 元   [unverified, conf=0.5, src=user]
← A5  毛利率 62%               [unverified, conf=0.5, src=user]
← A6  商圈范围为门店半径 1 公里    [unverified, conf=0.4, src=user]
```

> 👤 客流呢？你没问客流。

> 🤖 对，这是我缺的量。我补两个估算，明确标成 estimate、置信度给低——它们不是你给的，不能和你说的数一样算。

```
← A7  日均路过 3000 人次      [unverified, conf=0.3, src=estimate]
← A8  进店并购买转化率 4%      [unverified, conf=0.3, src=estimate]
```

**这就是"合作"的第一个具体差别。** 普通 agent 会把"我估的 4% 转化率"和"你说的 26 元客单价"混在一起算，最后给一个看不出成分的数字。这里两者分开记：`src=user` vs `src=estimate`，`conf=0.5` vs `conf=0.3`。

后面第 8 轮的门禁，拦的正是这两条 estimate。

---

### 第 5 轮 · 用户追问"这个数怎么来的"

> 👤 等一下，这个 -5 万是怎么出来的？我不信一个月能亏这么多。

> 🤖 我不复述，直接把账本里的卡片贴给你——上面写了它站在哪几条前提上。

```
$ ledger cite --id C5
← 卡片原文：
   [C5] 月净利 -5.00 万元
   取值：-49968 元/月
   状态：degraded　引用级别：降级可用
   依赖：A1、A2、A4、A5、A7、A8、C1、C2、C3、C4
   未核实前提：A1（月租金 8 万元）、A2（客单价 26 元）、A4（人工…）、A5（毛利率 62%）、
              A7（日均路过 3000 人次）、A8（进店并购买转化率 4%）
   注意：上游 A1、A2、A4、A5、A7、A8 未核实，引用须注明置信度
```

**注意 `降级可用` 这个词。** 结论能算出来，但它的六条前提一条都没核实，所以它只是"暂定可用"，不是"已成立"。模型不允许自己把它说成"算出来了，就是 -5 万"。

---

### 第 6 轮 · 用户改口径（全篇最关键的一次）

> 👤 房租我昨天问了中介，实际是 9.5 万，我之前说的 8 万是隔壁那间。

> 🤖 那 8 万作废。撤回后我只报账本算出来的影响面，不猜。

```
$ ledger retract --id A1 --reason '中介报价 9.5 万，原 8 万为隔壁房源'
← 3 条结论状态改变：
     C4  degraded → invalidated
     C5  degraded → invalidated
     C6  degraded → invalidated
← 不受影响 3 条：C1、C2、C3
```

> 🤖 被作废的是 C4, C5, C6——它们的计算里用了租金。C1、C2、C3 没受影响，因为它们不含租金。这就是账本存在的意义：我不用凭印象猜哪条要改。

**这段是本项目最该在答辩时演示的 30 秒。** 两件事同时发生：

1. 账本**算出了**影响面（不是查表，是在依赖图上做可达性分析）；
2. 账本**区分了**"必需依赖"。C1、C2、C3 在图上离 A1 很近，但它们不消费租金，所以一条都不该动。

普通 agent 会重算 C5，但 C6 那句"按当前口径无法回本"很可能就留在报告里了——**它不报错、不荒谬，只是不再成立。**

---

### 第 7 轮 · 作废的结论要显式撤回

> 👤 那按 9.5 万重新算。另外隔壁 B 铺子是 9.2 万，面积小一点，哪个更划算？

> 🤖 先把被作废的三条显式撤回、留档，再登记新前提重算。旧的那条租金我不会覆盖，它留在账上作为历史。

```
← C4 已撤回（历史留档，不再参与检测）
← C5 已撤回
← C6 已撤回
← A9  月租金 9.5 万元（A 铺，中介报价）
← A10 月租金 9.2 万元（B 铺，面积小 15%）
← C7  A 铺：月固定成本 12.30 万元  依赖 A9、A4
← C8  A 铺：月净利 -6.50 万元      依赖 C3、C7
← C9  B 铺：月净利 -6.20 万元      依赖 C3、A10、A4
```

**"撤回"和"删除"是两件事。** 删除会让报告失去历史，撤回是把它标成"曾经成立、现已作废"，留在账上。这也是为什么用户可以放心改口——改口不会掩盖他之前说过什么。

---

### 第 8 轮 · 用户要交付，门禁拦下

> 👤 行，我整理一下发给合伙人，就按 B 铺这个数。

```
$ ledger check        （C9 已标记对外输出）
← ok = False   （exit 1 = 不可交付）
   [error] export_gate: C9 已标记对外输出，但上游 6 条前提未核实，
           或自身状态为 degraded，不允许交付。
```

> 🤖 结论没错，但还不能发。拦下它的是「上游前提未核实」这一条——而且它把要核的是哪几个数，一个个点名了。

**这一行 `exit 1` 是整个 skill 的价值观：** 它不是"建议你再核实一下"，是一个机器可读的否决。上层想让报告出门，必须把这个 1 变成 0——**裁决权在脚本，不在模型。** 模型无权自己宣布"已验证"。

---

### 第 9 轮 · 补齐证据链，放行

> 👤 行，这些数的来源我都补给你：租金有中介书面报价、客单价是收银系统上月导出、人工按工资表、毛利看的上月报表。客流我上周实地数了三天，平均 3000。转化率问了隔壁奶茶店老板，4% 到 5%。

> 🤖 那逐个核验，每条都写清证据来源——不能只写「已确认」。

```
← A9  unverified → verified   证据：2026-10-30 中介书面报价单 No.2026-1030
← A2  unverified → verified   证据：2026-10 收银系统导出，客单价 25.8 元（取 26 元）
← A4  unverified → verified   证据：2026-10 工资表，4 人合计 28200 元
← A5  unverified → verified   证据：2026-09 财务报表，毛利率 61.4%（取 62%）
← A10 unverified → verified   证据：2026-10-30 中介口头报价，B 铺 9.2 万元
← A7  unverified → verified   证据：2026-10-26 至 10-28 实地计数，日均 3040
← A8  unverified → verified   证据：2026-10-29 邻店经营者访谈，区间 4%-5%

$ ledger check
← ok = True   （exit 0 = 可交付）  issues 共 0 条
← 统计：前提 10 条（已核验 7）、结论 9 条（有效 6、降级 0、作废 3）
```

> 🤖 现在可以发给合伙人了。而且这份材料的每个数从哪来，都写在账上。

**门禁逼出了证据清单。** 用户本来只想说"这些数我都核过了"，被拦下之后才不得不说出具体来源。最终这份材料每一条数都能追到一张单据或一次访谈——这不是 agent 的自觉，是脚本不让它通过。

## 五、对照：如果没有这个 skill

| 轮次 | 普通 agent | 装了账本的 agent |
|---|---|---|
| 第 5 轮问"-5 万怎么来的" | 复述一遍算式 | 贴依赖卡片，并指出 6 条前提均未核实 |
| 第 6 轮改租金 | 重算 C4、C5；C6 那句"无法回本"照旧留着 | 报"恰好 3 条作废、3 条不受影响" |
| 第 9 轮补证据 | 说"已确认" | 逐条写证据，放行时账上有 7 张凭据 |
| 交付 | 一份读起来很顺的报告 | 一份报告 + 一张"谁站在谁身上"的账 |

第二行第 6 轮那格，就是全部差别。**那个错误不会报错，也不会显得荒谬，它就静静躺在报告里。**

## 六、反面演示：不撤回、直接改前提会怎样

同一个场景，agent 图省事，用户改口后直接又登记一条新租金（没走 `retract`）：

```
$ ledger check
← ok = False
   [error] drift: 「rent」被赋予了 2 个不同取值（A1, A2），前提漂移。
← 账本拒绝让两个 rent 并存。
```

**它拒绝替用户决定哪个才对。** 账本不知道 8 万和 9.5 万哪个是权威值——它只能把冲突摆出来，让人先确认口径。如果脚本自作主张选一个，它就变成了另一个会静默出错的助手。

## 七、怎么自己跑一遍

```bash
python demo_scenario/run_scenario.py      # 完整 9 轮实录，含对照
```

看三处即可：第 6 轮的 `retract` 返回、第 8 轮的 `exit 1`、第 9 轮的 `ok = True`。

## 八、这个实例暴露出的两个真缺陷（已修，见 `docs/skill_self_eval.md` 第六节）

写这份实例时按完整会话走了一遍，踩到两个 demo 覆盖不到的问题：

1. **更正前提后永久判漂移** —— `retract 8万` 再登记 `9.5万`，同 symbol 被判"两个值并存"，任何"用户更正数据"的正常流程都过不了门禁。
2. **已作废结论永久污染门禁** —— 撤回前提后下游结论自动作废，但 `check` 对已作废结论持续报 error，连显式撤回也不消失；账本一旦有历史，就永远 `ok=false`。

两处都已修复，并连带修正了数据集 D10 的重复标注（14 → 13 处埋点）。C 组仍 13/13 = 100%、阴性对照误报 0。

**这两条只有"真的用一遍"才会发现**——这也是为什么这份实例不只是文档，它本身就是一次测试。
