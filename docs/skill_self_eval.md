## 一、评价体系是怎么来的

这门课的四层结构决定了"好的 skill"不能只看功能：

| 层 | 对应讲义 | 落到评分维度 |
|---|---|---|
| 决策层 | 讲 1 | G 触发与泛化——什么时候该被叫起来 |
| 方法层 | 讲 2 | A 规范与结构——五段式、负面触发、确定性脚本 |
| 裁决层 | 讲 3 | B 确定性证据链——谁有权说"通过" |
| 元层 | 讲 5–8 | E 可评测性——能不能被外部安全地测评与改进 |
| 工程实现 | 讲 7 | D 鲁棒与安全、F 可读可改性 |

七维权重与理由：

| 维度 | 权重 | 为什么给这个权重 |
|---|---|---|
| **A 规范与结构** | 15% | 决定 agent 能否正确加载和不误触发 |
| **B 确定性证据链** | 20% | 本项目的立身之本：裁决权必须在脚本 |
| **C 功能正确性** | 20% | 检测器错了，后面全是空的 |
| **D 鲁棒与安全** | 15% | 讲 7 的"伤害有界"：一个坏输入不能打爆输出 |
| **E 可评测性** | 15% | 讲 5–8 主线：不能被测评的 skill 无法改进 |
| **F 可读可改性** | 10% | 演化面越小越安全 |
| **G 触发与泛化** | 5% | 权重低是因为它只影响"用不用得上"，不影响"用了对不对" |

### B 确定性证据链：5.0 / 5

**证据**

```bash
python examples/demo.py                        # 门禁拦下 → exit 1
python scripts/ledger.py check                 # 退出码就是裁决
```

- ✅ 是否可交付**只由 `check` 的退出码决定**，SKILL.md 第 3 条明写"模型不得自行宣布已验证"
- ✅ 三档退出码语义固定：0 通过 / 1 不可交付 / 2 输入非法
- ✅ `cite` 返回的是**卡片原文**，SKILL.md 规定"把卡片原文贴出来，不要自己复述依赖关系"——防止模型二次加工时失真
- ✅ 禁止行为里明确禁掉模糊措辞："不得使用『基本不受影响』『大致仍然成立』"
- ✅ 禁止编造 `--evidence`：没有证据就留空并说明未核实

这是全篇最强的一维，没有扣分理由。

### D 鲁棒与安全：4.5 / 5

**证据（本轮修复前 → 修复后）**

| 探针 | 修复前 | 修复后 |
|---|---|---|
| `verify --id A9`（未知 id） | exit 2 + 结构化 JSON ✅ | 不变 ✅ |
| `add-premise --value abc` | **Python traceback，exit 1** ❌ | exit 2 + `{"ok": false, "error": "输入非法：..."}` ✅ |
| `add-premise --text ""` | **被接受，exit 0** ❌ | exit 2 + `"前提陈述不能为空"` ✅ |

修复内容（`scripts/ledger.py`）：主入口加统一异常护栏，任何未预期异常都转成结构化输出 + 退出码 2；`add-premise` / `add-claim` 拒绝空陈述。

**扣分点**：
- 没有输入长度上限（`--text` 可以塞几十 MB），"伤害有界"只做到了异常边界，没做到资源边界。
- 未做并发写保护（两个进程同时写同一账本会互相覆盖）。

## 五、这套评分体系自身的局限

1. **权重是我定的**：换个权重，分数会变。所以本报告的价值不在"94.4"这个数字，而在**每一维的证据链和扣分理由**——评委可以不同意权重，但可以复核证据。
2. **自评有美化倾向**：对抗办法是强制"每一分都要有可复现命令"。D 维的扣分就是我自己跑探针跑出来的，不是事后补的。
3. **缺少外部效度**：没有第三方用这个 skill 做过真实任务。"在有 skill / 无 skill 两种条件下，同一任务的返工轮数差多少"这个指标最有说服力，但需要真实用户，本轮未做。

## 六、v1.0.1 修复记录：写「使用实例」时踩出的两个缺陷

这两个缺陷不是跑单点测试找到的，是**真的按一次完整用户会话走一遍**才暴露的——三段 demo 都没有"更正后重新登记"和"撤回多次后仍想交付"这两条长路径。

| # | 缺陷 | 触发方式 | 修复前 | 修复后 |
|---|---|---|---|---|
| 1 | **更正前提后永久判漂移** | `retract A1`（租金 8 万）→ `add-premise`（租金 9.5 万，同 symbol） | `check` 报 `drift: rent 被赋予 2 个不同取值（A1, A9）`，exit 1。**任何"用户更正数据"的正常流程都过不了门禁。** | 已撤回的前提视为历史条目，不参与同符号并存比较。 |
| 2 | **已作废结论永久污染门禁** | 撤回 A1 → C4/C5/C6 自动 `invalidated` → 再 `check` | 对 `invalidated` 结论持续报 `contamination` error；即使显式 `retract C4` 也不消失。**账本一旦有历史，就永远 `ok=false`。** | 已撤回的结论退出全部检测；`contamination` 只对"被污染但仍未撤回"的结论报警——恰好保留了数据集里那 3 处污染埋点的检出能力。 |

连带修正：数据集 **D10** 的 `drift` 与 `contamination` 埋点指的是同一处病（A2 已撤回、C1 仍引用 A2），属重复计数。按新语义只计 `contamination`，**埋点总数 14 → 13**，C 组 13/13 仍 100%，阴性对照仍误报 0，人工基线 7/13 = 53.8%。

**为什么把这条写进报告而不是藏起来**：缺陷 2 说明"检测器本身也会制造死锁"——一个只会报警、不会消警的门禁，用户体验上是不可交付的。能定位并修掉这类"纪律自身的副作用"，比拿满分更能说明这个 skill 被真正用过。
